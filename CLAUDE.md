# VKTE — Правила проекта (99 жёстких правил)

Проект: STM32H745 Ballistic Corrector (dual-core прошивка + KiCad PCB + host-софт).
Эти правила обязательны для каждого изменения. Главный закон — правило 99.

## Архитектура и контекст (1–10)

1. Всегда рассматривай проект как критически нагруженную распределённую систему с высокими требованиями к отказоустойчивости.
2. Не принимай на веру текущую реализацию; ищи скрытые архитектурные дефекты, циклические зависимости и нарушения SOLID/DRY/KISS.
3. Каждое изменение кода сверяется с исходным ТЗ проекта (HLD_BOARD_INTEGRATION.md, IMPLEMENTATION_BACKLOG.md, HARDWARE_DESIGN.md).
4. Запрещён hardcode конфигураций, путей, таймаутов и эндпоинтов — только config.h / параметры / env.
5. Абсолютная изоляция модулей: интерфейсы взаимодействия явно типизированы (заголовки с полным API, никаких неявных extern).
6. Любое глобальное состояние — потенциальный баг: требует обоснования и инкапсуляции (static + функции доступа).
7. Проектируй с расчётом на масштабирование и асинхронное выполнение (M7 real-time / M4 async — контракт IPC неприкосновенен).
8. Мёртвый (неиспользуемый) код удаляется немедленно (прецедент: неиспользуемая huber_loss удалена).
9. Версионирование API: изменения контрактов обратно совместимы (формат сессий во Flash — версионируемый заголовок).
10. Все архитектурные решения документируются в коде строгими комментариями (Doxygen для C, Docstring для Python).

## Бескомпромиссный Code Review (11–25)

11. Действуй как скептичный эксперт-ревьюер: ищи не то, как код работает, а где и при каких условиях он сломается.
12. Проверяй обработку всех edge cases. Пустые catch / `except: pass` — архитектурное вето.
13. Анализируй race conditions при параллельном/асинхронном выполнении (особенно IPC-кольцо M7↔M4 и HSEM).
14. Выявляй утечки памяти, неэффективные аллокации и блокировки потоков.
15. Строгая типизация везде, где поддерживается; никаких `any`/`void*`-трюков без крайней необходимости.
16. Корректное освобождение ресурсов (дескрипторы, сокеты, соединения) через RAII/контекстные менеджеры.
17. Идентифицируй проблемы производительности: N+1, O(n²) на больших данных, избыточные перевычисления.
18. Ищи скрытые побочные эффекты в «чистых» функциях.
19. Валидация входящих данных на границах системы (Data Boundary Validation) обязательна.
20. Запрещено логирование чувствительных данных (PII, пароли, токены, ключи).
21. Контролируй цикломатическую сложность; при избытке ветвлений — рефакторинг на подфункции.
22. Запрещены deprecated-библиотеки и подходы.
23. Кодировка строго UTF-8; консистентная обработка локалей.
24. Логирование структурировано и содержит контекст для трассировки (trace_id/session_id).
25. Сравнивай алгоритмы по производительности; требуй оптимальных структур данных.

## Тестирование и Coverage 95%+ (26–50)

26. Целевое покрытие тестами — не менее 95% строк для каждого модуля (текущее по firmware/src: 94.7%; добивать при каждом изменении).
27. Не принимаются тесты только «счастливого пути» — негативные сценарии обязательны.
28. Для каждого найденного бага — изолированный unit-тест, воспроизводящий проблему, ДО исправления (TDD).
29. Граничные значения обязательны: нули, отрицательные, пустые коллекции, максимумы типов.
30. Mock/stub — только для внешних недоступных систем (HAL, железо). Бизнес-логика — на реальных или in-memory двойниках (симуляторы регистров/Flash как в tests/unit_tests).
31. Интеграционные тесты для взаимодействия модулей (драйвер + session_manager и т.п.).
32. Тесты детерминированы: не зависят от порядка запуска, системного времени, сети.
33. Каждый тест очищает своё состояние (tearDown/cleanup; в C — переинициализация модульного состояния).
34. Запрещены мок-тесты, тестирующие сам фреймворк моков.
35. Покрытие асинхронных задач, очередей и фоновых воркеров (IPC-кольцо, batch-flush).
36. Assertions точные, а не `assert result is not None`.
37. Property-based тесты там, где применимо для инвариантов.
38. Тестирование ретраев, таймаутов и деградации (retry после сбоя Flash — прецедент в test_session_manager).
39. Стресс-тестирование ключевых узлов (заполнение кольца/буферов до отказа).
40. Запрещён hardcode задержек (sleep) в асинхронных тестах — события и поллинг состояния.
41. Тестирование миграций данных (формат сессий: прямой и обратный переход).
42. Покрытие обработчиков сигналов/прерываний (WWDG early warning — прецедент).
43. Мутационное тестирование там, где поддерживается стеком.
44. Покрытие парсеров конфигурации и валидаторов env-переменных.
45. Изоляция тестов: без разделяемого мутабельного глобального состояния (или явный порядок, как в test_m4_ipc).
46. Контроль скорости тестового набора; медленные тесты оптимизируются.
47. Тестирование восстановления после сбоя питания/падения хранилища (remount-тест session_manager — прецедент).
48. Тесты кэширования и инвалидации кэша.
49. Явное покрытие всех веток if/else/switch, включая default (corrupted-phase тест shot_assembler — прецедент).
50. Отчёт покрытия (gcovr) фиксируется в каждом PR/коммите.

## Безопасность и защита данных (51–70)

51. Проверка на OWASP Top 10 (инъекции, XSS, CSRF, SSRF, небезопасная десериализация).
52. Все SQL-запросы параметризованы.
53. Аутентификация/авторизация проверяются на уровне каждого эндпоинта/метода.
54. Криптостойкость: запрет MD5/SHA1 для паролей; только проверенные крипто-библиотеки.
55. Секреты изолированы от кодовой базы (менеджеры секретов, зашифрованные env).
56. Защита от переполнения буфера и некорректного приведения типов в низкоуровневых модулях (границы буферов в драйверах — CRC32, bounds-check).
57. Ограничения размеров входящих payload (защита от DoS).
58. Rate limiting на критических точках входа.
59. Валидация и санитизация путей к файлам (защита от Path Traversal).
60. Корректные CORS и заголовки безопасности (CSP, HSTS, X-Frame-Options) для веб-компонентов.
61. Аудит зависимостей (supply chain, lock-файлы).
62. Безопасная обработка загружаемых файлов (проверка содержимого, изоляция хранилища).
63. Защита от brute-force и скрапинга.
64. Логирование событий безопасности (сбои авторизации, попытки доступа).
65. Принцип наименьших привилегий для учёток, токенов, соединений.
66. Запрет жёстко закодированных тестовых учёток и бэкдоров.
67. Безопасное межсервисное взаимодействие (mTLS, подпись запросов, валидация JWT).
68. Защита от timing attacks: сравнение секретов за константное время.
69. Очистка памяти после работы с чувствительными данными.
70. Регулярный аудит прав доступа к инфраструктуре.

## Производительность и оптимизация (71–85)

71. Минимизация латентности и максимизация пропускной способности (бюджет M7: <20 мс измерение→оценка, <5 мкс enqueue).
72. Пулы соединений для БД, внешних API, очередей.
73. Эффективные алгоритмы поиска/сортировки на больших объёмах.
74. Индексы БД для всех полей выборок/джойнов/сортировок.
75. Кэширование «горячих» данных с чёткой политикой инвалидации (metadata_cache — прецедент; инвалидация через metadata_save).
76. Запрет блокирующего I/O в критических real-time путях (Flash I/O — только на M4, вне пути M7).
77. Контроль давления на память: без избыточных аллокаций в циклах (в прошивке — статические буферы).
78. Пагинация для всех списковых API.
79. Эффективная сериализация (бинарные форматы для высокочастотных путей — measurement_record_t).
80. Контроль памяти фоновых процессов/воркеров.
81. Сжатие сетевого трафика и оптимизация статики.
82. Таймауты на все внешние вызовы и обращения к железу (в т.ч. поллинг WIP у Flash — TODO таймаута обязателен к реализации).
83. Отказоустойчивые очереди с подтверждением доставки (IPC-кольцо: full → отказ, не потеря).
84. Корректность балансировки нагрузки.
85. Отсутствие дублирующих вычислений (мемоизация чистых функций при необходимости).

## Инженерия, документация и процессы (86–99)

86. Исчерпание логических аргументов перед принятием компромиссных решений; компромисс фиксируется письменно.
87. Документация обновляется параллельно с кодом (HLD/backlog/README — в том же коммите).
88. Атомарные коммиты: одно изменение — одна логическая задача с понятным описанием.
89. Соответствие стайлгайду проекта (C99 -Wall -Wextra -Wpedantic без ошибок; Python — PEP8).
90. Технический долг не появляется без явного тикета/записи в backlog (IMPLEMENTATION_BACKLOG.md).
91. Ревью независимым экспертом перед слиянием в основную ветку.
92. Воспроизводимость сборки на чистом окружении (CMake из чистого build-каталога; PCB — идемпотентные генераторы tools/gen_pcb_*.py с встроенным гео-DRC).
93. Актуальность и безопасность файлов зависимостей.
94. Детальные шаги развёртывания/сборки в README.md.
95. Корректность миграций при переключении версий (формат Flash-сессий).
96. Мониторинг здоровья приложения (watchdogs, PAT, счётчики диагностики).
97. Чистота логов: без мусорных отладочных выводов в продакшн-коде.
98. Ретроспектива архитектурных решений при масштабировании ×10.
99. **Главный закон: если код не покрыт тестами на 95%+, содержит архитектурные слепые зоны или расходится с ТЗ — он не имеет права находиться в продакшене.**

## Специфика проекта (обязательный контекст)

- Хост-тесты: `cmake -B build -DBUILD_TESTS=ON -DENABLE_COVERAGE=ON && make -C build && ctest --test-dir build`; покрытие: `gcovr --filter 'firmware/src/' --exclude 'firmware/src/main.c' --exclude 'firmware/src/system_init.c' --object-directory build build`.
- I/O-хуки драйверов — weak-символы: тесты переопределяют их симуляторами устройств; HAL-интеграция заменяет тела по TODO-меткам.
- PCB редактируется ТОЛЬКО через генераторы `tools/gen_pcb_placement.py` / `tools/gen_pcb_routing.py` (идемпотентные, с гео-DRC-аудитом, который обязан выдавать 0 нарушений перед записью). Ручная правка `.kicad_pcb` вне маркер-блоков запрещена.
- Критический путь: Gerber lock 2026-08-11; пиновка J4 и позиции крепежа — контракт совместимости v1.x/v2.0, менять запрещено.

## Нервная система автономии (обязательные артефакты)

- **`state_journal.md`** — журнал состояний: обновлять в конце КАЖДОЙ итерации (фаза → сделано → нерешённое → следующий шаг), только после прохождения валидации.
- **`validation_protocol.md`** — чек-лист самопроверки: переход к следующей задаче бэклога запрещён, пока не пройден.
- **`.claudeignore`** — фильтр контекста: build-артефакты, дампы и бинарники не читать.
- **`context_map.json`** (генерируется `tools/gen_context_map.py`) — карта include-зависимостей: перед правкой файла смотри, кто от него зависит.
- **`docs/AUTONOMY_PLAYBOOK.md`** — 99 лайфхаков автономии (7 параметров × 14 + Золотое правило 99: при внутренней уверенности <90% — остановиться и задать один точный вопрос инженеру).
