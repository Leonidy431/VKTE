# AUTONOMY_PLAYBOOK.md — 99 лайфхаков автономного агента

Итог «Симпозиума Перипатетиков» (дизайнер → критик → аналитик → синтез):
отброшена антропоморфная лирика, принята машинная логика + управление
контекстным окном. 7 параметров × 14 правил + Золотое правило.

Артефакты нервной системы: `state_journal.md`, `validation_protocol.md`,
`.claudeignore`, `context_map.json` (генерируется `tools/gen_context_map.py`).

## P1. Сжатие контекста (Context Density) — 1–14

1. Не переписывай файл целиком — выводи только diff или изменённые функции.
2. Структурируй базу знаний тегами-секциями (`<core_logic>`, `<UI>`).
3. Раздели ТЗ на «горячее» (текущий спринт) и «холодное» (архитектура).
4. Без извинений и введений — только код и сухие логи.
5. Периодически: summary диалога в 500 токенов → новая сессия с него.
6. Громоздкие данные (логи, дампы) — сжато или только заголовки.
7. Аббревиатуры частых команд: [V]=validate, [R]=refactor.
8. История слияний и merge-guardrails — в отдельный справочник, не в активное ТЗ.
9. Структура проекта — через `tree -I 'node_modules|.git|build'`, не копипастой путей.
10. При переполнении контекста — ответ в JSON (принудительное сжатие смысла).
11. Глубина анализа старого кода — максимум 3 уровня импортов.
12. Удаляй комментарии, дублирующие очевидное имя функции.
13. Перед передачей логов вырезай пустые строки и лишние табы.
14. Не анализируй файлы старше месяца без изменений, если задача не про ядро.

## P2. Детерминированность (Determinism) — 15–28

15. Роль задаётся до задачи («Ты — Senior Embedded/Cloud Architect…»).
16. Конкретные версии языка/фреймворка (C99, CMake ≥3.20, KiCad 7).
17. Chain-of-Thought в `<thought_process>` строго ДО кода.
18. Негативные промпты: явный список запрещённых библиотек и паттернов.
19. Штрафные баллы: `any`/`void*`-трюк = задача провалена.
20. Псевдокод перед боевой реализацией сложной логики.
21. Стиль именования зафиксирован (C: snake_case; без права отклонения).
22. Big-O в комментариях к циклам над большими массивами.
23. Edge cases в ТЗ списком Given-When-Then.
24. Запрет устаревших API.
25. Формат ошибок: [ERROR] → [CAUSE] → [SOLUTION].
26. Стоп-слова: при их генерации — прервать подход, запросить человека.
27. Перед каждым архитектурным решением — возврат к архитектуре в CLAUDE.md.
28. 100% покрытие типов в сигнатурах до реализации тел.

## P3. Самоисцеление (Error Recovery) — 29–42

29. Промпт-рефлексия: «найди 3 уязвимости в своём коде, исправь».
30. Failure-тесты ДО функционала.
31. Ошибка из консоли → сначала причина без кода, затем 2 пути решения.
32. Circuit Breaker на себя: 3 промаха подряд → запросить контекст.
33. Fallback для любых сетевых/внешних запросов.
34. Запрет «тихого падения»: все исключения логируются с контекстом.
35. Merge conflict → пошаговый план разрешения, не финальный файл.
36. Падение теста → анализ стек-трейса с конца (глубочайший вызов).
37. Алиас debug_deep: развернуть строку в 10 строк с промежуточным логом.
38. Миграции БД/схем — только со скриптами rollback.
39. Решение ломает CI/CD → сначала патч пайплайна.
40. Проверка race conditions в асинхронных задачах.
41. Проверка лимитов памяти (OOM) в скриптах обработки больших данных.
42. Распознавай циклические зависимости, выноси общее в абстракции превентивно.

## P4. Управление состоянием (State Management) — 43–56

43. Каждый ответ начинается с `<current_state>` (этап бэклога).
44. `git status` перед каждой сложной задачей.
45. Checkpoint = успешный билд; команда «Rollback to Checkpoint X».
46. todo_temp.md для мелких подзадач внутри крупной фичи.
47. Глобальное состояние не меняется без явного разрешения в CLAUDE.md.
48. state_journal.md обновляется только после прохождения линтеров/тестов.
49. [STATE DUMP] → вывести все активные переменные окружения.
50. Побочные эффекты изолируются в отдельные тестируемые модули.
51. Сложные UI/API проектируются как FSM.
52. Облачные БД: схема транзакции описывается до реализации.
53. Идемпотентные скрипты: двойной запуск не ломает систему.
54. Логирование смены состояний на уровне эндпоинтов.
55. В конце сессии — bash-скрипт инициализации среды для следующего сеанса.
56. Явное разделение Dev/Test/Prod; всегда уточнять текущее.

## P5. Токен-эффективность (Token Efficiency) — 57–70

57. Шорткоды вместо развёрнутых промптов: Refactor(performance, CPU).
58. .claudeignore максимально агрессивен (svg, lock, csv-дампы, build).
59. Вместо файла целиком — интерфейсы и сигнатуры.
60. Не выводить неизменённые блоки импортов.
61. Системные промпты и ТЗ — на английском (плотнее токенизация).
62. Короткие конструкции там, где не вредит читаемости.
63. Повторяющиеся блоки в ТЗ схлопывать: «… (аналогично блоку А) …».
64. Из JSON-массивов скармливать 2–3 объекта, не 1000.
65. README не генерируется до готовности проекта на 90%.
66. Лимит длины промежуточных ответов (≈500 токенов).
67. Длинные логи сжимать регулярками (без таймстемпов и INFO).
68. Директива: No pleasantries. Code only. Diff format.
69. Многоступенчатость: сначала номера строк с ошибкой, потом патч этих строк.
70. Конфиги инфраструктуры — в YAML (плотнее JSON).

## P6. Интеграция цепочек (Tool Chaining) — 71–84

71. Автоматизируй собственные решения bash-скриптами (прецедент: tools/gen_pcb_*.py).
72. Стороннее API → сначала curl-тест.
73. Контракт (Swagger/OpenAPI) до кода.
74. CI-workflow генерируется параллельно с серверной логикой.
75. JSON-RPC команды для промежуточных скриптов-исполнителей.
76. Цикл с профилировщиком: код → Flame Graph → оптимизация.
77. Docker — только multi-stage сборки.
78. Секреты — только Secret Manager / .env.local, никогда в коде.
79. Для каждого эндпоинта — Postman-коллекция или .http файл.
80. Цепочка: парсер → данные → анализ аномалий этих данных.
81. Микросервисы: контракт gRPC/REST до кода сервисов.
82. Healthcheck-эндпоинты для любых изолированных систем.
83. Линтер в цикле без участия человека: код → линт → лог → правка.
84. Развёртывание сетей узлов — конфиги для каждого узла списком.

## P7. Изоляция и безопасность (Sandboxing) — 85–98

85. Zero Trust: валидировать любые входящие данные.
86. eval() и динамическое выполнение строк — запрещены любой ценой.
87. CORS + Rate Limiting в любых публичных API.
88. Только параметризованный SQL / ORM.
89. Локальные bash-скрипты — в песочнице (chroot/контейнер).
90. В Dockerfile — не root (USER appuser), кроме крайней необходимости.
91. npm audit / аудит зависимостей в пайплайне.
92. Маскирование PII в системах логирования.
93. Токены/ключи — только через CI/CD-переменные.
94. Защитные буферы от переполнения при обработке больших массивов.
95. Least Privilege для доступа к БД.
96. Только подписанные/проверенные Docker-образы.
97. CSP при создании фронтенда.
98. Скрейпинг — ротация User-Agent/IP, обработка HTTP 429.

## 🌟 P0. Золотой мета-хак — Правило 99

99. **Правило Делегирования Сомнений**: если внутренняя оценка вероятности
    успешного выполнения кода ниже 90% — ОСТАНОВИСЬ, не пиши код, задай ровно
    один точный, изолированный вопрос инженеру для прояснения слепой зоны.
    Автономия без тормозов — это саморазрушение.
